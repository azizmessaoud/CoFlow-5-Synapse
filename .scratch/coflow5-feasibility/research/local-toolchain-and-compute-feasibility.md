# CoFlow-5 local toolchain and compute feasibility

**Decision date:** 2026-09-20  
**Envelope:** 2–3 students, 12 weeks, Windows/WSL laptops, no paid cloud  
**Evidence policy:** official Eclipse SUMO documentation; official framework documentation/source; first-party reproducibility and benchmark guidance. All capacity figures below are explicitly estimates until the Tier 0 smoke test replaces them.

## Executive decision

CoFlow-5 Tier 0 is feasible locally **without a GPU** if it is kept to one small grid, deterministic baselines, a parameter-shared MLP DQN, compact logs, and process-parallel headless simulation. SUMO is the likely bottleneck: its microscopic simulation is effectively single-core, and a GPU does not accelerate it.[S7] Use **64-bit Python 3.11, one exact pinned SUMO release, PyTorch CPU, TraCI for GUI/debugging, and measured libsumo for headless batches**.

Start on **native Windows** because the repository is on `C:` and SUMO provides official Windows binaries and wheels.[S1][S2] Consider WSL2 only for an earned Linux/container dependency; if selected, clone into `/home/...`, because Microsoft advises against running Linux file-intensive work from `/mnt/c`.[S12]

libsumo removes TraCI socket overhead and is generally faster, but the gain depends on the API call pattern and some subscriptions may be slower.[S3][S4] It is therefore a benchmarked choice, not an assumption. Each parallel libsumo simulation must live in its own process.[S3]

Shared DQN is the primary learned controller. MAPPO is a bounded comparator only after Tier 0 is frozen. Small MLP PPO/DQN workloads can run on CPU; first-party Stable-Baselines3 guidance explicitly recommends CPU plus subprocess environments for non-CNN PPO.[S16] GPU use is justified only if profiling shows learner updates, rather than SUMO rollout, dominate wall time.

**Redis, PostgreSQL/pgvector, MLflow, LangGraph, and an open-weights LLM are not mandatory.** MLflow is optional and can use local SQLite.[S20] The rest solve distribution/RAG/explanation problems outside Tier 0. The LLM is the first scope cut and must never enter the control path.

## 1. Installation and supported compatibility

| Component | Recommended baseline | Evidence/caveat |
|---|---|---|
| OS | Native Windows 10/11 x64 first; WSL2 Ubuntu second | SUMO, PyTorch, and PostgreSQL support current Windows.[S2][S9][S21] |
| Python | **3.11.x x64** | Official `libsumo` wheels require Python 3.9+; current PyTorch Windows guidance lists 3.9–3.12. LangChain, if later used, requires 3.10+.[S1][S9][S24] |
| SUMO | Pin one exact stable release across all students and runs; the official page advertises 1.27.1 at report date | Do not leave the project constraint at `>=1.24`. Log version, config hash, and git commit.[S1][S2] |
| SUMO Python | Matching exact `eclipse-sumo` or matching `traci`, `sumolib`, `libsumo` packages | A different `$SUMO_HOME/tools` can shadow the intended TraCI package; record `traci.__file__`.[S1][S5] |
| PyTorch | Stable CPU/CUDA wheel from the official selector, pinned after resolution | NVIDIA CUDA is recommended for acceleration, not required.[S9] |
| Packaging | `venv` + `pip` + lock/constraints file | SUMO's FAQ recommends vanilla Python and warns that Anaconda can disrupt binary search paths.[S6] |

Compatibility gate:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install eclipse-sumo==<PIN> traci==<PIN> sumolib==<PIN> libsumo==<PIN>
# Install the exact CPU/CUDA torch command generated by the official selector.
python -c "import traci, sumolib, libsumo, torch; print(traci.__file__, torch.__version__, torch.cuda.is_available())"
sumo --version
```

Do not blindly install all SUMO distributions if `eclipse-sumo` already supplies the selected layout; the requirement is one consistent, locked install. Source builds add Visual Studio/CMake/SWIG risk and are unnecessary.

### Windows versus WSL2

**Native Windows advantages**

- Lowest setup burden for the current working tree.
- Official prebuilt SUMO installer/ZIP and wheels.[S1][S2]
- Straightforward native PyTorch CPU/CUDA and PostgreSQL installation.[S9][S21]
- SUMO expects same-version, same-input, same-seed runs to reproduce across Windows/Linux/macOS, subject to documented exceptions.[S14]

**Native Windows constraints**

- Multiprocessing uses `spawn`; workers need an import-safe `if __name__ == "__main__":` entry point.[S10][S16]
- PyTorch CUDA IPC is unsupported on Windows. Workers should return CPU/NumPy batches, never shared CUDA tensors.[S10]
- libsumo GUI does not work on Windows. Use `sumo-gui` + TraCI for visual diagnosis and libsumo headless.[S3]
- Redis Open Source's official Windows path is Docker, adding overhead.[S22]

**WSL2 trade-offs**

- Better Linux/container ergonomics; Docker Desktop uses a WSL2 backend.[S13]
- Docker GPU access on Windows requires WSL2 and supported NVIDIA drivers.[S13]
- Keep code and write-heavy outputs under `/home`; cross-OS filesystem access is significantly slower.[S12]
- WSL does not make one SUMO process multi-core.

**Decision:** remain native through the smoke test. Compare WSL only if Docker is assessed, a required package lacks a stable Windows wheel, or a same-workload test from WSL ext4 is materially better. Do not maintain two active production environments.

## 2. TraCI, libsumo, and multiprocessing

Official documentation establishes:

1. TraCI runs SUMO as a server over sockets. Slowdown depends on call count/type, client computation, and language.[S4]
2. libsumo embeds a TraCI-like API and removes socket communication. A script can often switch via `import libsumo as traci`.[S3][S5]
3. libsumo does not support normal `traci.init`/`connect`, multiple libsumo clients, or normal Windows GUI operation. Parallel Python instances require multiprocessing.[S3]
4. SUMO's microscopic core is effectively single-core; `--threads` does not yet give meaningful general speedup. Routing has separate thread options.[S7]
5. Independent simulator processes—not threads inside one simulation—are the useful scaling unit.
6. SUMO logs expose wall duration, TraCI duration, real-time factor (RTF), and vehicle updates per second (UPS).[S8]

SUMO's illustrative Bologna test took 8 s without TraCI, 90 s with plain position retrieval, and 42 s with subscriptions.[S4] This proves call shape matters; it is not a transferable CoFlow-5 speed ratio.

Safe worker architecture:

- Parent schedules experiments and writes aggregate metadata only.
- Spawn workers. Each child imports/starts exactly one libsumo instance, owns a unique output directory, and closes in `finally`.
- Pass serializable configuration; return compact episode summaries/file paths, not simulator objects or CUDA tensors.
- Bound PyTorch/BLAS threads per worker to avoid oversubscription.
- Start at `workers = min(4, physical_cores - 1)` and measure 1/2/4-worker scaling.
- Use `spawn` on Windows and WSL for one code path. PyTorch warns that `fork` with background threads/accelerators can deadlock or fail.[S11]
- Cache static topology and phase data; prefer lane/junction aggregates over per-vehicle polling.
- Batch/subscribe only after measurement: SUMO notes subscriptions are not always faster under libsumo.[S4]
- Use 1 s simulation steps but make A1 decisions at the specified 5–10 s epoch.

## 3. Shared DQN and MAPPO compute

### Shared-policy DQN

A 4×4 grid can batch 16 junction observations through one small MLP. CPU inference should fit the proposed 100 ms budget, but that is a smoke-test hypothesis. Tiny unbatched GPU inference can lose to CPU because transfer and kernel-launch overhead are not amortized.

Likely cost order:

1. SUMO stepping and state extraction;
2. replay insertion/sampling;
3. environment process coordination;
4. neural updates.

Replay memory needs discipline. For a 128-float observation, observation plus next observation alone is `2 × 128 × 4 = 1,024` bytes/transition. One million transitions is therefore at least ~1.0 GB before actions, masks, indexing, and container overhead—roughly 1.2–2.0 GB in an efficient array design and far more as Python objects. This is dimensional, not measured. On 8 GB RAM, cap replay at 100k–250k or use memory-mapped arrays.

### MAPPO

MAPPO adds a centralized critic, on-policy rollout storage, advantages, multiple PPO epochs, and sensitivity to rollout/minibatch settings. The authors' official implementation defaults to parameter sharing, supports subprocess rollouts, selects CUDA only when requested/available, and otherwise uses CPU.[S17]

- Rollout remains CPU/SUMO-bound.
- CPU-only MLP MAPPO is technically viable; non-CNN PPO is primarily a CPU workload in first-party framework guidance.[S16]
- GPU helps only when enough environments create large update batches.
- Record rollout length, workers, update epochs, minibatches, clipping, parameter sharing, environment interactions, and tuning budget for a fair comparison.
- Weak-laptop path: DQN receives the multi-seed study; MAPPO is a short integration proof or is cut.

### Reproducibility

- Pin software, OS path, machine class, and dependency lock.
- Use explicit SUMO `--seed`; never use `--random` in reported runs. `runSeeds.py` supports explicit parallel seed lists.[S14]
- Seed Python, NumPy, framework/environment, and PyTorch per worker.
- PyTorch does not promise identical results across releases/platforms or CPU versus GPU.[S15]
- For confirmation runs, disable cuDNN benchmarking and request deterministic algorithms where supported; expect a speed cost.[S15]
- Use common random numbers: pair every controller on the same scenario/demand seed.

## 4. Low/base/high resource envelope

### Assumptions

- One episode: 600 s warm-up plus 3,600 measured simulated seconds.
- SUMO step 1 s; A1 action every 5 s.
- One “scenario cell” is network × demand × incident/failure regime.
- 16 controlled junctions and small MLPs; no images or graph transformers.
- Unknown effective headless RTF planning bands: **low 4×, base 15×, high 40× per worker**, including controller calls but excluding large learner updates.
- Provisional 2–4 worker efficiency: 70–90%.
- Pure rollout projection:

  `hours = decisions × 5 / (measured_RTF × 3,600 × workers × measured_efficiency)`.

| Envelope | Hardware assumption | Training scope | Final evaluation | Retained storage | Interpretation |
|---|---|---|---|---|---|
| **Low / weak laptop** | ≤4 physical cores, 8 GB RAM, SSD, no GPU; 1–2 workers | DQN 100k–250k decisions × 3 seeds; MAPPO ≤50k integration run | 1 grid × 3 demand cells × 3 controllers × 5 paired seeds = **45 episodes** | **10–30 GB** | Honest Tier 0 pilot; not a broad generalization claim |
| **Base / expected** | 6–8 physical cores, 16 GB RAM, 150+ GB free SSD; optional 6–8 GB NVIDIA GPU; 3–5 workers | DQN 250k–750k × 5 seeds; MAPPO 250k–500k × 3 seeds on one cell | 1 grid × 6 cells × 4 controllers × 10 paired seeds = **240 episodes** | **50–150 GB** | Credible course evaluation; DQN primary |
| **High / pooled** | 2–3 machines, each 8+ physical cores/16–32 GB RAM; one 8–12 GB GPU; 500 GB pooled SSD | DQN/MAPPO 0.5–1.5M × 5–10 seeds; one realistic snippet after grid freeze | 2 networks × 6 cells × 4 controllers × 15–20 seeds = **720–960 episodes** | **200–500 GB** compact; multi-TB with bulk FCD | Stretch ceiling, not commitment |

Five seeds is a pilot, ten paired final seeds per cell is the base target, and 15–20 is stretch. These are design choices, not universal statistical minima. Use pilot paired-difference variance to set a documented precision/power target; never choose seed count to obtain significance.

Example only: RTF 15, four workers, 80% efficiency:

- one 1-hour episode takes 240 s on one worker;
- 240 episodes take about 5 h aggregate;
- 500k five-second decisions take about 14.5 h rollout plus learner/checkpoint time.

At RTF 4, two workers, 70% efficiency, the same 500k decisions take about 124 h before learner overhead. Therefore no training promise is credible before Tier 0 measurement.

## 5. Logs and storage

SUMO's compact trip/statistic outputs should be primary. Vehicles unfinished at a fixed end are omitted unless `--tripinfo-output.write-unfinished` is set; official guidance explains their inclusion in comparisons.[S18] Enable unfinished-trip accounting in every reported run.

Retain every run:

- git/config/scenario/controller hashes; exact software/OS; seed;
- aggregate statistics and tripinfo including unfinished vehicles;
- decision events at the 5–10 s control epoch, not full state every second;
- KPI row, collisions/teleports/errors, performance metrics;
- selected checkpoints/training curves.

Retain only for sampled diagnosis:

- full FCD trajectories and per-second per-vehicle emissions;
- profiler traces;
- videos/GUI capture.

Measure one episode and calculate:

`total = median_bytes_per_run × planned_runs × 1.5 + checkpoints + source data`.

FCD risk estimate: 1,000 active vehicles × 3,600 s × 100–250 serialized bytes ≈ **0.36–0.90 GB/run** before compression/filesystem effects; across 240 runs, 86–216 GB for FCD alone. This is dimensional. SUMO supports output period, probability, edge/shape, and attribute filters.[S8][S19] Sample FCD at 5–10 s on at most ten diagnostic runs.

Practical quotas:

- ordinary evaluation run: `<25 MB`;
- training run: `<1 GB` excluding replay snapshots;
- keep best-by-predeclared metric, last, and milestone checkpoints only;
- warn at 70% and stop at 85% of assigned experiment storage.

## 6. Docker

Docker is feasible but not Tier 0-required. Docker Desktop's WSL2 backend requires supported 64-bit Windows, WSL ≥2.1.5, virtualization, and 8 GB RAM.[S13] That minimum leaves little room for an IDE, SUMO workers, PyTorch, and databases on an 8 GB laptop.

Use Docker after native smoke-test success:

- useful: reproducible headless API/database/demo packaging;
- poor early use: SUMO GUI, high-rate logs mounted to `C:`, one service per training worker;
- keep Docker/WSL code and volumes in WSL ext4.[S12]
- Windows Docker GPU support requires WSL2 and supported NVIDIA drivers.[S13]
- pin image digests and package versions.

Weak-laptop path: omit Docker during development; provide one late CPU-only image only if assessed.

## 7. Mandatory, optional, and scope-risk services

| Technology | Status | Value | Cost/risk and gate |
|---|---|---|---|
| SUMO + TraCI/libsumo | **Mandatory** | Simulation/control interface | Pin exactly; benchmark TraCI versus libsumo |
| Python + PyTorch | **Mandatory for learned A1** | DQN/MAPPO | CPU suffices for Tier 0 |
| Compact files + manifest | **Mandatory** | Reproducible evidence | Parquet/JSON/CSV plus DuckDB/SQLite are enough |
| Redis | **Optional / early scope risk** | Split-process/host Streams demo | Windows normally adds Docker; in-process queues meet one-machine needs.[S22] Add only for a tested split-host requirement |
| PostgreSQL + pgvector | **Optional / scope risk** | Durable multi-user RAG metadata/search | Service/schema/backups/memory. pgvector HNSW uses more memory and builds faster only while fitting `maintenance_work_mem`.[S23] Add only after a frozen RAG need beats local exact search |
| MLflow | **Optional, lower risk** | Run UI and artifacts | Local SQLite and filesystem artifacts are supported; PostgreSQL is unnecessary here.[S20] Add only if it replaces—not duplicates—the manifest |
| LangGraph | **Optional / scope risk** | Stateful advisory explanation workflow | Officially a long-running stateful agent framework.[S24] Plain functions suffice initially; add only after Tier 0 freeze |
| Open-weights LLM | **Optional / highest risk** | Offline explanation/summarization | Downloads, RAM/VRAM, latency, evaluation, licensing. Last addition; never control SUMO |

For scale: 7B parameters at 4 bits are ~3.5 GB raw weights before quantization metadata, runtime buffers, KV cache, tokenizer, and application memory. Hugging Face documents that 8-bit roughly halves and 4-bit quarters weight memory, but runtime overhead remains.[S25] A “7B 4-bit” model is not a safe 8 GB-machine assumption and competes with simulation on 16 GB. No LLM fine-tuning belongs in this scope.

## 8. Precise first Tier 0 smoke test

This one-day deliverable replaces all throughput, worker, RAM, storage, and GPU estimates before DQN implementation.

### Fixed artifact

- deterministic 4×4 grid, 16 signals;
- 1 s step; 600 s warm-up + 3,600 s measured;
- fixed-time controller plus deterministic observation/action stub;
- seeds `{11, 22, 33}`;
- one non-gridlocked demand level;
- aggregate statistics and tripinfo with unfinished vehicles;
- no GUI, FCD, screenshots, or verbose step log;
- hashes of network, routes, additional files, and config.

### Measurement matrix

Run one unrecorded warm-up then **three recorded repetitions** per cell:

1. standalone `sumo` without Python control (floor);
2. TraCI with exact planned observation calls;
3. TraCI with applicable subscriptions/batching;
4. libsumo with identical loop;
5. libsumo at `N = 1, 2, min(4, physical_cores - 1)` independent workers;
6. fastest safe API + shared 2×128 MLP inference + mask + compact log + replay insertion every 5 s;
7. 10,000 learner updates from a prefilled compact buffer on CPU and, if available, GPU.

If WSL is seriously considered, repeat cells 4–6 from a clone under `/home`, never `/mnt/c`.[S12]

### Record

- wall/simulated seconds, RTF, UPS, TraCI duration;
- CPU time/utilization, peak RSS/private bytes, bytes written;
- observation, inference, mask/arbitration, logging, update p50/p95/p99;
- workers, aggregate episodes/hour, parallel efficiency  
  `E_N = throughput_N / (N × throughput_1)`;
- import/start/close failures;
- arrived/unfinished/teleported vehicles, travel/wait/stops, ordered action hash;
- actual replay bytes/transition and checkpoint size;
- versions, paths, hashes, hardware.

Use wall time with warm-up. Use `torch.utils.benchmark.Timer` for update/inference microbenchmarks because it warms up, controls threads, and synchronizes accelerators; use the profiler only to explain a bottleneck.[S26]

### Acceptance gates

1. **Correctness:** same observation schema and ordered stub actions under TraCI/libsumo; exact deterministic KPI equality where possible, otherwise a predeclared tolerance and explanation.
2. **Latency:** observation→mask→action→log p95 `<100 ms` on the slowest supported machine.
3. **Capacity:** projected training + final evaluation `≤25%` of remaining calendar wall time on committed machines.
4. **libsumo:** select only if stable and ≥20% faster end-to-end than best TraCI, or materially simpler operationally.
5. **Workers:** largest `N` with `E_N ≥0.70`, no memory pressure, no p95 regression; reserve one physical core.
6. **GPU:** use for RL only if learner time improves ≥25% and end-to-end training ≥10%.
7. **Storage:** measured complete matrix ×1.5 must fit the quota; otherwise reduce fields/frequency first.

Rerun this baseline after changing SUMO version, network, observations, logging, decision frequency, or execution platform.

## 9. Explicit cuts

### No GPU

Keep shared DQN, baselines, masks, headless simulation, CPU workers, compact logs, paired statistics. Cut/bound:

- MAPPO to one cell × three seeds after DQN, or omit if projected above one week;
- all LLM fine-tuning/real-time generation;
- local LLM to an optional small quantized offline demo; otherwise templates + retrieval;
- GNNs, LSTM forecasting, images, and large hyperparameter sweeps;
- Docker GPU work.

### Weak laptop (≤4 physical cores or 8 GB RAM)

- Native Windows; no Docker/Redis/PostgreSQL.
- One or two simulator workers; replay 100k–250k.
- One 4×4 grid, three demand cells, three primary controllers, five paired pilot seeds.
- DQN only for reported learned results; MAPPO is integration-only.
- One short diagnostic FCD; no replay snapshots; prune checkpoints.
- MLflow only if measured RAM/storage fit; otherwise JSON/CSV manifests.
- No local generative LLM; Synapse becomes reason-code templates and retrieval-only explanation.

If fastest safe RTF `<4`, reduce observation calls or grid first. If projected three-seed DQN remains above 72 wall-hours, deliver baselines + safety + a short learning feasibility run. Do not cut paired evaluation, failure accounting, or unfinished trips.

### Cut order

1. open-weights LLM and LangGraph;
2. PostgreSQL/pgvector and Redis;
3. Dockerized development;
4. learned A4/LSTM and realistic-network scale-up;
5. MAPPO breadth, then MAPPO;
6. extra scenario/seed breadth based on documented precision;
7. **never cut** baselines, safety mask, seed/version manifests, paired evaluation, unfinished-trip handling, or failure reporting.

## 10. Twelve-week recommendation

- **Week 1:** lock environment; run smoke test; choose OS/API/workers/log budget.
- **Weeks 2–3:** fixed-time, actuated, Max-Pressure, masks, KPI parity, manifests.
- **Weeks 4–6:** shared DQN; three-seed pilot; freeze observation/reward.
- **Weeks 7–8:** paired DQN/baseline evaluation and robustness. Tier 0 complete.
- **Weeks 9–10:** A2/A3/A5 plus ablations only if Tier 0 is complete.
- **Week 11:** bounded MAPPO only if capacity gate passed.
- **Week 12:** reruns, report, optional packaging. Synapse uses surplus capacity only.

## Bottom line

The credible project is a **small CPU-first traffic-control experiment**, not the complete production-pattern stack. The hard chain is SUMO → safe A1 adapter → baselines → compact evaluation → shared DQN. libsumo, multiprocessing, GPU, Docker, Redis, PostgreSQL/pgvector, MLflow, LangGraph, and an LLM are choices gated by measurement; only the first two are likely performance enablers, and none should weaken experimental rigor.
